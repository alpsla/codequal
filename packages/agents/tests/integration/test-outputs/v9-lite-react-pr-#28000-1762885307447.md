### 🟠 Javascript Lang Security Detect Child Process

**Severity**: HIGH | **Tool**: semgrep | **Found in**: 5 files | **Category**: EXISTING_REST

---

#### 📋 What is this issue?

The code invokes the child_process module with a function argument 'cmdArg', which may allow command injection if the input is derived from user-controllable data. This is a direct call to exec or spawn with dynamic command construction.

#### 🎯 Why does it matter?

An attacker could inject malicious shell commands by manipulating the 'cmdArg' parameter. For example, if 'cmdArg' contains ' && rm -rf /', it would execute arbitrary OS commands with the privileges of the running process. This can lead to complete system compromise.

#### 🔍 Common causes:

- Direct use of child_process.exec or child_process.spawn with user-provided input
- Lack of input validation or sanitization for command arguments
- No sandboxing or isolation of command execution environment

#### ⚠️ Impact if not fixed:

This vulnerability can result in full system compromise, data exfiltration, and persistence mechanisms being established. It violates security compliance standards such as PCI DSS, HIPAA, and SOC2, which mandate protection against unauthorized command execution.

#### ⚡ Risk Assessment

**Overall Risk**: 🟠 **HIGH RISK**

High priority - could cause significant problems in production

**Category**: Security  
**Focus**: Protecting against attacks, vulnerabilities, and unauthorized access

#### 📍 Representative Example

**Location**: `fixtures/packaging/build-all.js` (Line 19)

**Code**:

```javascript
    16 |     cwd: path,
    17 |     stdio: 'inherit',
    18 |   };
>   19 |   const result = child_process.spawnSync(cmdArg.cmd, cmdArg.args, opts);
    20 |   if (result.status !== 0) {
    21 |     throw new Error(`Failed to build fixtures!`);
    22 |   }
```

#### 🔧 How to Fix

Replace direct child_process calls with a secure alternative by validating and sanitizing all inputs, using a whitelist of allowed commands, or employing a sandboxed execution environment. Prefer using a dedicated command runner with strict input validation or avoid shell execution entirely where possible.

**Recommended Code**:

```javascript
// Before: Vulnerable code
// const { exec } = require('child_process');
// exec(cmdArg, (error, stdout, stderr) => { ... });

// After: Secure implementation
const { exec } = require('child_process');
const allowedCommands = ['ls', 'pwd', 'date'];

function safeExec(command, args = []) {
  if (!allowedCommands.includes(command)) {
    throw new Error('Command not allowed');
  }
  // Validate and sanitize args
  const sanitizedArgs = args.map(arg => arg.replace(/[^a-zA-Z0-9._-]/g, ''));
  return exec(`${command} ${sanitizedArgs.join(' ')}`);
}
```

**Best Practices to Follow**:

- Avoid using child_process with user-controlled input entirely
- Implement a whitelist of allowed commands and parameters
- Sanitize all inputs using regex or allow-list validation before command execution
- Use sandboxed environments or containers for command execution if necessary

#### 📋 What is this issue?

The template variable is used as an unquoted attribute value, which creates a potential XSS vulnerability. If the variable contains malicious content, it can be interpreted as executable JavaScript by the browser.

#### 🎯 Why does it matter?

An attacker could inject custom JavaScript handlers by manipulating the template variable's value. For example, if the variable contains `onclick=alert(1)`, the browser would execute the script when the element is clicked. This leads to persistent XSS in web applications.

#### 🔍 Common causes:

- Unquoted attribute value in HTML template
- Direct insertion of user-controlled data into DOM attributes
- Lack of sanitization or encoding of dynamic values

#### ⚠️ Impact if not fixed:

This vulnerability allows attackers to perform XSS attacks, potentially stealing session cookies, redirecting users to malicious sites, or executing arbitrary JavaScript in the victim's browser. It can lead to account takeovers and data breaches, violating OWASP Top 10 A03:2021 - Injection and A07:2021 - Identification and Authentication Failures.
